# Format: <version>\t<filename>   (tab-separated; # and blank lines ignored)
#
# WHY THIS FILE EXISTS
#   The 239 migrations below were written as flat, unordered files and applied
#   by hand. "Which migrations ran in prod?" was answered by grepping Railway
#   logs for Postgres error codes (42703 / 42501). This manifest + the
#   public.schema_migrations table replace that with a real answer.
#
# HOW THE INITIAL ORDER WAS DERIVED (versions 0001-0239, frozen 2026-08-03)
#   The true historical application order is unrecoverable — files were applied
#   by hand and out of band. What IS recoverable is the DEPENDENCY order, which
#   is the only property a from-scratch rebuild needs: a file that ALTERs table
#   T must come after the file that CREATEs T.
#
#   Each file's produced objects (CREATE TABLE/VIEW/TYPE) and required objects
#   (ALTER, REFERENCES, CREATE INDEX/POLICY/TRIGGER, GRANT, INSERT, UPDATE)
#   were extracted, a DAG built, and a topological sort run with a
#   deterministic tiebreak. Result: 0 cycles, 0 ordering violations — every
#   file lands after everything it depends on.
#
#   This is a RECONSTRUCTION, not history. Treat versions 0001-0239 as one
#   baselined block (`migrate.py baseline`), not as a replayable timeline.
#
# NOT SELF-CONTAINED
#   A few base tables (`recordings`, `admin_users`, `auth.users`, `storage.*`)
#   are not created by any file here — they predate the directory or belong to
#   Supabase. A from-scratch rebuild needs the Supabase base schema first.
#
# ADDING A MIGRATION
#   Use `python scripts/migrate.py new <slug>` — it writes the .sql stub and
#   appends the next version here. Never renumber, never reorder, never delete
#   a line: applied versions are recorded in the DB by version + checksum, so
#   editing history silently desynchronises every environment.
#
# See docs/MIGRATIONS.md for the full workflow.
