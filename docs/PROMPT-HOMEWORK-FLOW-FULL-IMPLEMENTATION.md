# Prompt: Full homework flow implementation (for another LLM)

Use this document to implement or align the full homework/coaching flow. It lists **what is already implemented** in the backend, **what is missing or unclear**, and **clarifying questions** the product/backend owner should answer before implementation.

---

## Intended flow (product description)

1. **warmup_task → recording_1 → context_1 + score_1** (no scoring applied to warm-up recording in the sense of “grading” – score_1 is computed from recording_1).
2. **n_metrics** are hardcoded; they score recording_1 → **performance_score_1**.
3. **Focus task** is chosen from tasks that have a **score_1** threshold: if user scores 0.5, they only get focus_tasks with threshold ≤ 0.5.
4. **context_1** is derived from recording_1 (e.g. transcribed and summarized) and stored.
5. User answers **metric_questions**; answers are stored.
6. **Task text** is **generated by AI** from: context_1 + metric_answers + chosen focus_task (using a **framework** – product needs help defining it).
7. User sees the **task**, records **recording_2**; recording is transcribed → **context_2**; **score_2** is computed with the same n_metrics.
8. **score_transcription** is computed from transcript + metric_answers (product needs help defining how).
9. **after_recording_questions** (post_recording_questions) are asked; answers stored.
10. **report_history** is generated from: context_2, score_2, score_transcription, post-recording answers. It contains **score_end** (product may want a specific formula) and **context_end** (coach-like report).
11. Report is **sent to admin**. Admin adjusts scoring, edits warmup/focus/post_recording_questions, and maintains **student_context** (coach-only bio). These updates influence the next run (e.g. **warmup_task** selection).

Below: what exists in code vs what’s missing, then a short implementation plan and explicit questions.

## What is already implemented (backend)

- **Warm-up task**
  - Per-student warm-up tasks: `v2_warm_up_tasks` (and pool `v2_warm_up_task_pool`) with `max_performance_score`.
  - Selection: `v2_get_assigned_warm_up_task(user_id)` uses **last `performance_score_end`** and picks a warm-up whose `max_performance_score` ≥ that score (with ±3% tie-break; first-time = easiest). Implemented in `services/db.py` and `services/v2_flow_service.py` (`select_warm_up_task`).

- **Recording_1**
  - Upload and transcribe: `homework_submit_recording_1` (route `/session/<session_id>/recording-1` or similar). Transcript stored on recording; WPM and filler count computed.

- **context_1**
  - **context_short** = AI summary of recording_1 transcript (`openai_service.generate_context_short(transcript_text)`). Stored on session as `context_short`. No separate “context_1” name in DB; this is it.

- **score_1 (performance_score_1)**
  - **n_metrics** for recording_1: **3** metrics (pace from WPM, strength from loudness, fillers from count). `compute_performance_score_1(wpm, strength_raw, filler_count)` in `services/metrics_v2.py`. Result stored as `performance_score_1` on session.

- **Focus task selection**
  - Implemented using table **`v2_tasks`** (columns: `id`, `title`, `prompt_text`, `min_task_score`, `max_task_score`, `is_active`), **not** `v2_focus_tasks`. Logic: `select_focus_task_for_performance_score_1(all_tasks, performance_score_1, assigned_task_ids)` – eligible tasks where `min_task_score <= performance_score_1`; optional filter by `assigned_next_task_ids` from overrides. In `routes/homework.py` after recording_1 upload.

- **Metric questions and answers**
  - **3** metric questions from `v2_metric_questions` (positions 1–3). Shown in task block; user submits `answer_1`, `answer_2`, `answer_3` (or `metric_answer_1/2/3`). Stored in session as `metric_answers`: `{ answer_1, answer_2, answer_3 }`. Route: `homework_submit_metric_answers`.

- **Final task generation (AI)**
  - **generate_final_task(context_short, focus_task_title, focus_task_prompt, metric_answer_1, metric_answer_2, metric_answer_3)** in `openai_service.py`. Produces “2 sentences”: (1) Based on [context], your task is [focus_task]; (2) Focus especially on [metric answers]. No formal “framework” beyond this prompt.

- **Recording_2**
  - Upload, transcribe, store transcript on recording. WPM, fillers, strength (if available) computed. **score_2**: `compute_metrics_v2` with **5** metrics (pace, strength, fillers, emotion_achieved, keywords_used). `emotion_achieved` comes from post-recording “emotion_achieved_check” answer; keywords from transcript (currently empty list unless provided). Result stored as `performance_score_2` on session and on recording (`performance_score_v2`, `performance_metrics_v2`).

- **context_2**
  - **Not** stored as a separate summary. Recording_2’s **transcription_text** is the raw “context” for the report. There is no second `generate_context_short`-style summary for recording_2 (no “context_2” field).

- **Post-recording questions (after_recording_questions)**
  - Per-student list: `v2_student_post_recording_questions`. Questions shown after recording_2; answers submitted in `homework_submit_post_answers`. Answers passed to report generation as `post_answers`.

- **Report (report_history / context_end)**
  - **generate_final_report** builds the coach report from: transcript (recording_2), post_answers, homework_context_short (context_1), homework_metric_answers, homework_performance_score_1/2, admin_context. Report text stored in `v2_reports` and appended to session’s **context_long_entries** (report history). Admin can **PATCH** session report: append or replace entries (`/admin/students/<user_id>/sessions/<session_id>/report`).

- **score_end (performance_score_end)**
  - **Current formula:** `(performance_score_1 + performance_score_2) / 2`, clamped 0..1. Stored on session as `performance_score_end`. Used for next warm-up selection (last score).

- **Admin panel (backend)**
  - Overrides: `assigned_next_task_ids`, etc. (no longer `assigned_post_question_ids` for post-recording).
  - Speaker profile: `v2_speaker_profiles` (main_goal, motivation, coach_notes, etc.) – **PUT** speaker-profile.
  - Report history: session’s `context_long_entries`; admin can read and PATCH (append/replace).
  - Warm-up / focus / post-recording: CRUD and sync for task-warm-up, task-focus, post-recording-questions (pool + per-student). Focus in **homework flow** still uses **v2_tasks**, not v2_focus_tasks.

- **Admin context for report**
  - **get_user_admin_context(user_id)** returns: `professional_notes`, `professional_notes_report_tech` (custom_instructions, max_words), `professional_notes_specific_questions`. This is used in **generate_final_report**. It does **not** include `v2_speaker_profiles` (coach_notes, etc.); that’s a separate table.

- **Warm-up influenced by “updated parameters”**
  - No explicit “send to user” API. Next time the user starts a session, `v2_get_assigned_warm_up_task` reads **last performance_score_end** and **v2_warm_up_tasks** from DB. So any admin change that affects overrides or DB state (e.g. manual score override, if added) would influence the next run implicitly.

## What is missing or unclear (must be defined before full implementation)

1. **score_transcription**
   - **Status:** Not implemented. Product asked “how to calculate.”
   - **Needed:** Exact definition. Examples: (a) LLM score 0..1 from transcript + metric_answers; (b) rule-based alignment between transcript and self-ratings; (c) part of an existing metric (e.g. one of the 5). Where it is stored (session? recording?) and whether it is shown in the report or only used in score_end.

2. **score_end formula**
   - **Status:** Implemented as `(performance_score_1 + performance_score_2) / 2`.
   - **Needed:** Confirm if this is final or if score_end must include **score_transcription** (e.g. weighted average of score_1, score_2, score_transcription) or other inputs.

3. **context_2**
   - **Status:** Only recording_2’s raw **transcription_text** exists. No separate “context_2” summary (no second context_short).
   - **Needed:** Decide if context_2 = transcript only, or if an AI summary (e.g. generate_context_short for recording_2) should be stored and used in the report.

4. **Focus task source (v2_tasks vs v2_focus_tasks)**
   - **Status:** Homework flow uses **v2_tasks** (min_task_score ≤ performance_score_1). Admin panel manages **v2_focus_tasks** (per-student, max_performance_score). Two different tables and semantics.
   - **Needed:** Decide: (a) Unify on **v2_focus_tasks** for the flow (pick by max_performance_score ≥ score_1 or equivalent), or (b) Keep v2_tasks for flow and document the split, or (c) Migrate v2_tasks data into v2_focus_tasks and switch flow to v2_focus_tasks.

5. **“Framework” for AI task generation**
   - **Status:** Single prompt in **generate_final_task** (2 sentences: context + focus task + metric answers). No structured rubric or template system.
   - **Needed:** Define the “framework”: e.g. fixed template with placeholders, multiple templates by focus type, or a stricter rubric the LLM must follow. Then implement or extend generate_final_task accordingly.

6. **student_context (coach-only bio)**
   - **Status:** Two candidates: (a) **v2_speaker_profiles** (coach_notes, main_goal, etc.), (b) **get_user_admin_context** (professional_notes, custom_instructions, specific_questions). Report uses admin_context (b); admin UI often shows speaker_profile (a).
   - **Needed:** Define “student_context” precisely: one of these, or a single merged view (e.g. “student_context” = speaker_profile + professional_notes), and whether the report should use it and under what key.

7. **“Updated set of parameters sent to the user”**
   - **Status:** No explicit “send” step. Admin saves overrides and speaker_profile; next session load reads from DB (e.g. warm-up selection).
   - **Needed:** Clarify: (a) “Sent” = “persisted and used on next session start,” or (b) an actual push (email, in-app notification, or API the client polls). If (b), specify channel and payload.

8. **Admin “adjusts scoring”**
   - **Status:** No API to overwrite or adjust **performance_score_1**, **performance_score_2**, or **performance_score_end** from the admin. Report text can be edited (PATCH report).
   - **Needed:** Decide if admin can edit numeric scores (and which ones). If yes, add storage (e.g. session or recording) and APIs.

## Implementation plan (after questions are answered)

1. **score_transcription**
   - Define formula/source (LLM vs rules).
   - Add computation after recording_2 (and possibly after post-answers if it needs them).
   - Store on session (e.g. `score_transcription`) or on recording; expose in session/report APIs if needed.

2. **score_end**
   - If formula changes (e.g. include score_transcription), update `homework_submit_post_answers` (or the step that finalizes the session) and any docs.

3. **context_2**
   - If desired, add a step (after recording_2 transcribe) that calls something like `generate_context_short(recording_2_transcript)` and stores it (e.g. session.`context_2` or session.`context_short_2`). Use it in report generation if specified.

4. **Focus task source**
   - If switching to **v2_focus_tasks**: change homework flow to load per-student focus tasks, apply selection by max_performance_score (or agreed rule), and use selected task’s `text` (and optional fields) for generate_final_task. Deprecate or remove use of v2_tasks in this flow.

5. **AI task framework**
   - Implement the chosen framework (templates, rubric, or structured prompt) in or around **generate_final_task**; keep inputs: context_1, focus_task, metric_answers.

6. **student_context**
   - Unify on the chosen definition; ensure report and admin APIs use the same “student_context” (and optionally rename in API for clarity).

7. **“Send to user”**
   - If “sent” means more than “used on next load”: add the chosen mechanism (e.g. email with summary, or “params” payload for client) and document.

8. **Admin score adjustment**
   - If required: add fields and PATCH (or PUT) for session/recording scores and recalc or store score_end as admin-overridable.

## Clarifying questions for the product/backend owner

Answer these so another LLM (or dev) can implement the missing pieces without guessing.

1. **score_transcription**  
   How should it be computed? (e.g. LLM grade 0..1 from transcript + metric_answers; or a rule; or reuse one of the 5 metrics?) Where should it be stored (session vs recording)? Should it appear in the report and/or in score_end?

2. **score_end**  
   Keep `(score_1 + score_2) / 2`, or change? If change, give the exact formula (e.g. include score_transcription with weights).

3. **context_2**  
   Is recording_2’s raw transcript enough for the report, or do you want a separate AI summary stored as “context_2”? If yes, what field name and where used?

4. **Focus task in homework**  
   Should the flow use **v2_focus_tasks** (per-student, max_performance_score) instead of **v2_tasks** (min_task_score)? If yes, confirm selection rule (e.g. task eligible if max_performance_score ≥ performance_score_1).

5. **AI task “framework”**  
   What exactly should the framework be? (e.g. one fixed template, multiple templates by focus type, or a strict rubric with sections.) Any must-include phrases or structure?

6. **student_context**  
   Is “student_context” = speaker_profile (coach_notes, etc.), or professional_notes + report_tech + specific_questions, or a merge of both? Should the final report explicitly receive a “student_context” block?

7. **“Updated parameters sent to the user”**  
   Does “sent” mean only “saved and used on next session start,” or is there a real push (email, notification, or API)? If push, what is sent (e.g. new warm-up task, full config, report link)?

8. **Admin “adjusts scoring”**  
   Should admins be able to edit performance_score_1, performance_score_2, or performance_score_end? If yes, where are overrides stored and which APIs should expose them?
